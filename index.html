#01
Medium Behavioral
Tell me about a time you disagreed with a technical decision made by your team.
Answer
"We were building a new microservice and the team decided to use REST API for internal service-to-service communication. I had concerns about that approach given our performance requirements. I put together a quick benchmark comparing REST with gRPC for our specific payload sizes and latency targets. The data showed gRPC would cut our p99 latency almost in half. We switched the approach for internal calls and kept REST for external-facing endpoints. The performance improvement was real, and having the data took the personal edge out of the disagreement completely."
中文提示：考察冲突处理与数据驱动决策能力。使用STAR/SOAR结构：情境(Situation)、障碍(Obstacle)、行动(Action)、结果(Result)。强调用数据说话，而非情绪对抗。
#02
Hard System Design
Design a URL shortening service like bit.ly. Walk me through your approach.
Answer
"Before designing, I'd clarify requirements: Are we optimizing for read-heavy traffic? What's the expected scale? Assuming millions of DAUs, the core function is simple: take a long URL, generate a short key, store the mapping, and redirect users. For key generation, I'd use base-62 encoding of an auto-incrementing ID from the database, giving us enough unique combinations to last a very long time. For storage, a relational database works at moderate scale, but at very high traffic I'd add a caching layer like Redis in front of it, since most redirects are reads for popular URLs. The redirect service should be stateless and horizontally scalable behind a load balancer. I'd also implement rate limiting on the creation endpoint to prevent abuse. If we need analytics, we can asynchronously log redirect events to a data pipeline."
中文提示：系统设计经典题。回答框架：先clarify需求（读写比例、规模）→ 给出整体架构 → 深入关键组件（key生成、存储、缓存、负载均衡）→ 扩展讨论（限流、分析）。展示trade-off思考。
#03
Medium Technical
How do hash tables work, and how would you handle collisions?
Answer
"Hash tables use a hash function to map keys to array indices, providing O(1) average-case time complexity for insert, search, and delete operations. For collision handling, there are two primary strategies: 1. Chaining: Each bucket stores a linked list (or balanced tree) of entries with the same hash. When a collision occurs, the new entry is appended to the list. Simple to implement; performance degrades gracefully. 2. Open Addressing: When a collision occurs, probe for the next available slot. Methods include linear probing, quadratic probing, and double hashing. Requires a load factor threshold (typically 0.7) to maintain performance. In practice, modern implementations (like Java's HashMap) use chaining with trees for buckets that exceed a threshold (e.g., 8 entries), achieving O(log n) worst-case lookup."
中文提示：数据结构基础题。回答要点：哈希表原理（hash function → index）→ 碰撞原因 → 两种解决方案（链地址法/开放寻址法）→ 各自优缺点 → 实际应用中的优化（如Java HashMap的树化）。注意区分平均O(1)和最坏情况。
#04
Easy Behavioral
Describe a time you had to learn a new technology quickly to complete a project.
Answer
"During my last role, our team was tasked with migrating our reporting dashboard from a JavaScript-based charting library to Apache ECharts for better performance with large datasets. I had never used ECharts before, and we had a three-week deadline. My approach was: First, I built a minimal proof-of-concept over the weekend to understand the API surface and rendering model. Second, I set up a structured learning plan — one official doc section per day, paired with implementing one chart type. Third, I created a shared internal wiki with common patterns, gotchas, and code snippets for the team. By the end of the sprint, we'd migrated 80% of the charts and reduced average render time from 2.3 seconds to 340 milliseconds. The experience taught me that rapid learning is about focused experimentation, not passive reading."
中文提示：学习能力与主动性考察。使用SOAR结构：情境（项目需要新技术）→ 障碍（时间紧、零基础）→ 行动（POC快速验证、结构化学习计划、知识共享）→ 结果（提前完成、性能提升85%）。突出学习方法和可量化的成果。
#05
Hard System Design
How would you design a rate limiter for an API?
Answer
"Rate limiting protects services from abuse and manages traffic. Several algorithms exist, each with trade-offs: 1. Fixed Window Counter: Simple counter per time window. Problem: boundary spike — requests at the end of one window and start of the next can double the allowed rate. 2. Sliding Window Log: Track individual request timestamps. More accurate but memory-intensive at high throughput. 3. Token Bucket: Tokens refill at a steady rate; each request consumes one. Allows bursts up to bucket capacity while enforcing a sustained rate. Good balance of accuracy and efficiency. 4. Leaky Bucket: Requests enter at any rate but exit at a fixed rate. Smooths traffic but doesn't allow controlled bursts. For a distributed system, I'd use Redis with the sliding window counter approach — storing request timestamps in a sorted set with TTL equal to the window size. This gives us O(log N) operations and automatic cleanup. For high-traffic APIs, I'd add a local in-memory rate limiter as a first layer (fast rejection) before hitting Redis."
中文提示：分布式系统经典设计题。回答框架：明确目的（防滥用、限流）→ 对比多种算法（固定窗口/滑动窗口/令牌桶/漏桶）的优劣 → 给出分布式方案（Redis + Sorted Set）→ 扩展讨论（本地+全局双层限流、不同粒度的限流策略）。展示trade-off权衡能力。
